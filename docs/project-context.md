## What this is

**Groww Review Pulse**: a CLI agent that turns public Play Store reviews of the Groww app
into a **weekly one-page note**. It takes the top 3 themes, 3 verbatim quotes and 3 action
ideas, in 250 words or fewer. It publishes the note to a **Google Doc** and creates a
**Gmail draft** (never sent), both through an **MCP server**. The agent never holds a Google
credential.

It is a ten-stage pipeline. Each stage writes an artifact to `runs/<week>-<nn>/`, so any
stage can be replayed with `--from N`.

| # | Stage | Artifact | Deterministic? |
| --- | --- | --- | --- |
| 1 | ingest (file drop) | `01_raw.json` | yes |
| 2 | normalize + window + substance filter | `02_normalized.json` | yes |
| 3 | PII scrub | `03_scrubbed.json` | yes |
| 4 | classify into 5 themes (LLM) | `04_classified.json` | no, cached |
| 5 | aggregate, rank, quote candidates | `05_stats.json` | yes |
| 6–7 | draft the note (LLM) + validation gate | `06_note.json`, `07_validation.json` | no, gated |
| 8 | render | `pulse.md` | yes |
| 9 | append the week to the Google Doc (MCP) | `09_published.json` | — |
| 10 | create the Gmail draft (MCP) | `10_draft.json` | — |

The **run ledger** `runs/<id>/run.json` records every stage's timing, detail, token usage,
the doc URL and the draft id.

## Architecture in brief

```text
src/pulse/
├── cli.py            # Typer CLI: run, fetch, doctor, validate, models, themes, contract check
├── pipeline.py       # stage dispatch + preflight (MCP probe before any LLM spend)
├── orchestrator.py   # run dirs, artifacts, ledger -- imports nothing from ingest/analysis
├── config.py         # TOML + env -> typed Settings
├── llm.py            # LlmPort: GroqLlm, FakeLlm, NullLlm
├── ingest/           # file_drop, normalize (+ substance filter), play_store (pulse fetch)
├── analysis/         # scrub (PII), classify, aggregate, draft
├── rendering/        # render (markdown + blocks), validate (the gate)
├── publish/          # ports (DocsPort/GmailPort), docs (stage 9), gmail (stage 10), retry
└── mcp/              # contract, session (stdio + HTTP), discovery, adapters, errors
contract/google-workspace-mcp-0.1.json   # what the agent sends to / reads from the server
contract/archive/pulse-mcp-1.json        # superseded original contract (kept for reference)
tests/stubs/stub_mcp_server.py           # stand-in for the real server (stdio + HTTP)
config/{pulse,themes,mcp}.toml
```

**Layering rules that matter:**

- The pipeline depends on `publish/ports.py`, never on MCP directly.
- `mcp/adapters.py` is the only module that maps a port to a tool. Tool names come from
  `config/mcp.toml`.
- Nothing reads earlier than `03_scrubbed.json` before a model call or a publish.

## Data: what the real corpus looks like

The export covers 12,800 reviews over exactly 12 complete ISO weeks (2026-W30 → W41). It
has no reviewer identity fields.

- **After normalize and dedupe:** 8,812 reviews.
- **After the substance filter** (decided 2026-10-15: *English reviews of more than 8 words
  only*), **1,708 kept (19.4%)**. Removed:
  - 231 emoji or punctuation only;
  - 145 in a non-Latin script;
  - 471 romanized Hindi (Hinglish);
  - 6,257 with fewer than 9 words.
- **Rating skew:** 77% of raw reviews are 5★. In the kept subset, 1★ outnumbers 5★ (705 vs
  606). Short reviews are mostly praise, long ones mostly complaints, so the note must say
  its numbers describe *substantive* reviews. It does: "N substantive reviews of M in window".
- **Hinglish filter:** a deterministic, versioned word list (no language-ID library).
  Inspected by hand: no English review dropped out of 59; about 4% of kept reviews are
  still non-English.

Real classification (`openai/gpt-oss-120b` on Groq, 1,708 reviews, 43 batches):

| Theme | Share |
| --- | --- |
| `orders_execution` | 27.5% |
| `app_reliability` | 20.6% |
| `charges_support` | 20.1% |
| `payments_withdrawals` | 6.3% |
| `onboarding_kyc` | **3.9%** |
| unclassified | 21.5% (generic praise, mean 4.0★) |

## The MCP server, and how the agent uses it

The deployed server is a general-purpose Google Workspace server. It does **not** implement
the `pulse-mcp/1` contract designed in Phase 4, so the agent was adapted to it (option A).

| Server tool | Used by the agent? |
| --- | --- |
| `ping` | no; `initialize` already proves reachability |
| `docs_get_info(document)` | yes: the preflight probe and stage 9 |
| `docs_append_content(document, blocks[])` | yes: stage 9 |
| `gmail_create_draft(to[], subject, body, body_format)` | yes: stage 10 |
| `gmail_send_email` | **never.** The agent refuses to bind any tool matching `send`. |

**How publishing works now:**
- **One standing Google Doc** (`PULSE_DOC_ID`), created once by hand, because the server
  cannot create or find docs.
- Each week is **appended** as a section headed `Groww Review Pulse — <week>`.
- **Idempotency is the agent's own record.** If any run's `09_published.json` shows the week
  `appended` to that doc, it is skipped. Stage 10 likewise won't draft a week twice.
  `--republish` overrides both.
  Limitation: this is local state, so a clean checkout forgets it.
- Content goes over as **typed blocks** (`render_blocks`), with the same content as
  `pulse.md`. Quotes are checked verbatim before sending.

**Errors:** the server returns only prose messages, with no codes. The contract file holds
ordered rules mapping its fixed messages (from its `src/errors.ts`) to `AUTH_REQUIRED`,
`NOT_FOUND`, `PERMISSION_DENIED`, `UNAVAILABLE` and so on. When Google is unavailable, the
agent retries after the server's own retries.

**Preflight:** before stage 1, the agent connects, checks the server's name and semver, binds
the tools, and calls `docs_get_info` on the configured doc. This proves the token, the doc,
and Google authorization (one OAuth token serves both APIs) before any LLM spend.

## Bugs found and fixed (the non-obvious ones)

| Phase | Bug |
| --- | --- |
| P2 | The classification cache was saved only after the last batch. A dropped Groq connection lost every finished batch; it is now saved in `finally`. |
| P2 | The word floor kept exactly-8-word reviews ("at least 8", not "more than 8"), and emoji counted as words. |
| P3 | The model invented quote ids and star ratings. Provenance is now taken from the matched review, never from the model. |
| P4 | MCP SDK errors arrive as nested `ExceptionGroup`s, including the caller's own; `session.py` unwraps them. |
| P4 | The PII digit rule redacted ISO dates (it counted characters, not digits). |
| P5 | The ledger's `record_stage(**detail)` crashed when a stage's detail contained `status`. |
| P5 | Replaying into the run that published overwrote its `appended` record with `skipped`, so the next run appended the week again. |
| P5 | The SDK reports HTTP 401 as a generic error; the session now records 401/403 itself, so a wrong token says so. |
| P5 | Stage 8 rendered `pulse.md` without `corpus_total`, dropping the substantive-subset disclosure. |
| P5 | On real data the model mislabelled figures ("+5.6% week-over-week" for +5.6 pts vs an 11-week baseline). Figures are now printed by code; digits in the model's headline or summaries are rejected. |
| P5 | A failed re-draft left the old note on disk for `--from 9` to publish. Stage 6 now deletes it on abort. |

## Configuration and secrets

Secrets live **only** in `.env` (gitignored) or the environment. Config files only *name*
the variables. See `.env.example`.

| Variable | Purpose | Set? |
| --- | --- | --- |
| `GROQ_API_KEY` | stages 4 and 6 | yes |
| `PULSE_MCP_TOKEN` | bearer token for the live server; must equal the server's `MCP_AUTH_TOKEN` | **no** |
| `PULSE_DOC_ID` | the standing doc (a scratch doc for the first live run) | **no** |
| `PULSE_RECIPIENT` | Gmail draft recipient | **no** |

**Security notes:**
- The server's `MCP_AUTH_TOKEN` was rotated after an earlier one was pasted into a chat. The
  owner reports the live value differs from the replacement the server repo's notes mention,
  so **rotate it if there is any doubt**.
- Never paste a token into chat, a commit, or a doc. Prefixes included.
- The server's `DRY_RUN=false`: live writes are real. Do the first live run against a
  scratch doc.

## How to run

```bash
pip install -e ".[dev]"
pulse doctor                       # what is and is not ready
pytest -q                          # offline: no network, no real server

# Analysis only (stages 1-8, no MCP):
pulse run --dry-run --input data/raw/com-nextbillion-groww-2026-10-11.json --week 2026-W41

# Full pipeline against the in-repo stub (needs PULSE_RECIPIENT; the stub's doc is `stub-doc`):
PULSE_DOC_ID=stub-doc pulse run --mcp stub --input tests/fixtures/reviews_sample.json --week 2026-W41

# Against the live server, once the token and doc IDs are set:
pulse contract check               # live tools still accept what we send
pulse run --mcp live --week 2026-W41
pulse run --mcp live --week 2026-W41 --from 9 --run-dir runs/<id>   # republish an existing run
```

Stub state persists in `.cache/stub-mcp-state.json`; delete it to start from an empty doc.
